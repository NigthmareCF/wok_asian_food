# Arquitectura del core WOK

Estado: arquitectura objetivo, 2026-09-25. Véase [GAP_ANALYSIS.md](../project/GAP_ANALYSIS.md) para distinguir implementación de diseño.

## Límite y módulos

Un monolito modular Spring Boot es el único escritor transaccional de PostgreSQL. Web Cliente, Operativo, Administrativo y app Cliente consumen `/api/v1`; ningún frontend calcula el total definitivo, disponibilidad, permiso, impuesto o estado financiero. Los paquetes de dominio son `identity`, `customers`, `staff`, `tables`, `reservations`, `catalog`, `recipes`, `inventory`, `purchasing`, `production`, `availability`, `service`, `orders`, `kitchen`, `delivery`, `messaging`, `billing`, `payments`, `cash`, `invoicing`, `notifications`, `email`, `reports`, `settings`, `audit`, `integration`, `ai` y `vision`. Crear código en cada paquete sólo al implementar un caso de uso, sin clases vacías.

Los casos de uso coordinan transacciones cortas, repositorios y puertos. Los adapters externos (Meta, correo, banco, FEL, STT, runtime IA) no participan en la transacción SQL: se guarda estado local y outbox, se confirma y después trabaja un worker idempotente. `UUID`, `BigDecimal`, `Instant`, versionado, constraints e idempotencia son convenciones de dominio. Logs y DTO nunca contienen secretos, PAN/CVV, refresh ni datos de otro cliente.

La disponibilidad central y la conectividad externa se informan por separado. Actuator mantiene el health interno del core sin sondear proveedores; `GET /api/v1/admin/system/health` (ADMIN) informa `coreStatus` mediante `SELECT 1` y el estado/modalidad conocida de pagos, FEL, correo, IA y Meta. Los estados `MOCK`, `DISABLED`, `NOT_CONFIGURED` y `UNVERIFIED` describen la configuración presente; `connectivityVerified=false` evita presentar una selección/configuración como prueba de que una API externa responde. Sólo agregar un estado `READY` a una integración cuando exista una sonda real y segura.

## Capacidad y reservaciones

`OperationalCapacityService` recibe modalidad, instante, comensales y preorden; lee primero excepciones diarias activas de `DINE_IN`, después de `RESTAURANT`, y si no hay excepción usa horario semanal `DINE_IN` con fallback a `RESTAURANT`. Luego usa `OccupancyEstimator`. Devuelve `SUGGEST_OTHER_TIME` con hasta tres alternativas futuras que respetan apertura y anticipación mínima cuando el día está cerrado o la hora queda fuera de ventana; `REJECT` por menos de tres horas también ofrece espacios posteriores compatibles. Devuelve `REQUIRES_HUMAN_APPROVAL` cuando el horario es válido, mientras aún falten snapshots reales de mesas, personal, cocina, carga, producción, reservas y pedidos. Puede responder `ACCEPT` o `ACCEPT_WITH_CONDITIONS` al completar esas fuentes. Incluye `reasonCodes`, alternativas y mensaje público; la evaluación no reemplaza la transacción de confirmación, que debe revalidar bajo bloqueo/versionado antes de reservar recursos.

Reserva formal y solicitud digital de mesa exigen 3 h de anticipación. El umbral es condición necesaria, no aceptación automática. La tolerancia normal es 20 min. La ventana de servicio se consulta de `business_hours`; la configuración base es 14:00–22:00 de martes a domingo, con último ingreso normal ~21:15 y delivery externo ~21:00. El horario de cocina y la capacidad real aún requieren fuentes operativas configurables. Grupos grandes cerca del cierre requieren evaluación humana. El cierre se usa internamente, sin mensajes de expulsión al cliente. `POST /api/v1/public/reservations/evaluate` es público y orientativo; enviar la solicitud vuelve a evaluar y no confirma.

Los horarios semanales se mantienen desde `GET /api/v1/admin/business-hours` y `PUT /api/v1/admin/business-hours/{serviceType}/{weekday}`; excepciones diarias desde `GET/PUT /api/v1/admin/business-hours/overrides`. El endpoint requiere el permiso exclusivo `hours:manage` (concedido inicialmente a ADMIN), valida ventanas y zona `America/Guatemala`, registra actor/motivo/auditoría y aplica `expectedVersion`. La API pública `GET /api/v1/public/service-hours` comparte las ventanas efectivas con web/app. Las escrituras y las confirmaciones operativas usan locks advisory por semana/fecha y locks de fila compartidos cuando existen, de modo que también se serializan inserciones concurrentes de una excepción nueva.

Al confirmar una solicitud en `/api/v1/operational/reservations/{id}/decision`, Operaciones vuelve a validar que sigan quedando al menos tres horas y que el día/hora continúe dentro del horario semanal o override vigente y del último ingreso normal. Si la agenda cambió mientras esperaba revisión, la confirmación devuelve conflicto y conserva la solicitud pendiente para que el personal la rechace o coordine otro horario; no acepta una reserva contra política obsoleta.

Para asignar mesas a una reserva ya confirmada o ARRIVED, `GET /api/v1/operational/reservations/{id}/table-assignment-options` muestra capacidad/zona, estado actual, asignación propia y conflictos con otros rangos reservados. Es una lectura orientativa, protegida por `tables:manage`. Una asignación vigente se devuelve marcada como propia y las otras mesas no se ofrecen para reemplazarla; primero se debe liberar con el endpoint explícito. La consulta no bloquea ni reserva mesas; `POST .../{id}/table-assignments` vuelve a validar y la constraint de exclusión PostgreSQL decide conflictos concurrentes.

`OccupancyEstimator` usa rangos iniciales configurables: 1 persona 75–105 min; 2, 90–120; 3–4, 105–150; 5–8, 120–180; 9–12, 150–210; 13+, cálculo especial. No multiplica el baseline por persona. Guarda estimado y duración real para calibración.

## Flujos y invariantes

- **Cotización remota:** `POST /api/v1/client/order-quotes` calcula el precio vigente, guarda snapshots de producto/opciones/precio/horario y vence a los 12 minutos. Calcula por estación la demora de cola activa, preparación y ETA estimado; al enviar una solicitud pickup/delivery el consumo único del quote crea un hold temporal de carga por estación con expiración configurable (12 minutos base). Sólo los holds activos del mismo día de servicio en Guatemala y de horario anterior/igual afectan la estimación remota siguiente; solicitudes locales sin horario ignoran esos holds para preservar prioridad presencial. Cancelación/rechazo los libera; el worker los vence; aceptación los convierte antes de crear comandas para evitar doble contabilización. No se reserva inventario ni se omite la revisión humana y revalidación operativa.
- **Pedido:** borrador/carrito no reserva inventario. La aceptación revalida precio, opciones, stock, horario, capacidad y ETA en backend. Pedido aceptado/comandado no lo modifica directamente el cliente. Cambios conservan original, actor, motivo, revisión de comanda, recursos, ETA e impacto financiero; material consumido no retorna a stock por anulación económica.
- **Servicio:** `local`, `reservations`, `dine-in-online`, `pickup`, `delivery`, `online-orders`, `messaging`, `online-payments`, `production` tienen `ENABLED`, `MANUAL_APPROVAL`, `PAUSED` o `DISABLED` independientes. Override registra actor, motivo y vencimiento. En carga alta, mesas/presencial tienen prioridad sobre remotos.
- **Pago y caja:** una cuenta puede recibir pagos mixtos. Propina es separada de venta; comisión 3% y sugerencia 7% son configurables, no políticas hardcodeadas. `opening float` no es venta. En efectivo contra entrega, el pago cierra el saldo del cliente y queda en `courier_cash_collections`; sólo el courier asignado al despacho activo puede recibirlo. La caja no registra el dinero hasta que personal con `cash:manage` liquide la custodia en una sesión abierta; el depósito genera movimientos separados de venta y propina, auditados e idempotentes. `PaymentGateway` mantiene el puerto externo separado del cobro operativo; el intento online de delivery se persiste como `CREATED` junto con un evento outbox, y el worker llama al adapter fuera de la transacción SQL. Cliente recupera el estado más reciente con ownership validado; el adapter mock devuelve `PENDING` y nunca confirma captura. Aún no hay checkout ni proveedor productivo. Pasarela online sólo recibe token/intent; WOK no recibe PAN/CVV. El adapter productivo requiere webhook firmado y conciliación de estados `UNKNOWN` antes de reintentar operaciones ambiguas.
- **FEL:** el pool facturable de una atención limita la suma de drafts y de documentos `UNKNOWN`; propina fuera del pool sujeto a validación fiscal. Cada DTE se certifica independientemente mediante el puerto fiscal `FiscalProvider` y un worker/outbox. Los rechazos definitivos pasan a `FAILED`; sólo excepciones que el proveedor garantice como no aceptadas son reintentables. Toda excepción no clasificada deja el DTE en `UNKNOWN`, publica la tarea y detiene reintentos automáticos. Una persona con `invoices:manage` debe registrar referencia de consulta y confirmar si se certificó o no; sólo la confirmación auditada de “no certificado” encola un nuevo intento. El mock no representa certificación SAT ni consulta automática. XML original/certificado, PDF, acuse y hashes requieren completar almacenamiento de artefactos.
- **Mensajería:** webhook firmado, raw event, dedup, normalización, identidad externa verificada, conversación y mensaje. Canales separados; `SpeechToTextProvider` procesa audio validado. Enlaces externos usan token opaco `/go/{token}`.
- **IA:** `AiGateway` aplica una guarda inicial de alcance, resuelve horarios/estado de servicios con reglas y deja inference detrás de `AiProvider`. `AiToolBroker` expone sólo DTO públicos permitidos, sin SQL del modelo, y audita cada uso. `/internal/ai/**` requiere token de servicio, no se enruta por Nginx y queda apagado por defecto. Falla de IA produce template/handoff, no caída del core. OCR de comprobante nunca confirma pago. Estado y pendientes: [arquitectura de IA](../ai/ARCHITECTURE.md).

## API y seguridad

Separar rutas públicas, guest, client, operational y admin. Errores estables con `requestId`, validación de DTO, 401/403/409/422/503 diferenciados. OpenAPI documenta operación y permiso, no expone entidades JPA. Los endpoints internos de IA no pasan por el ingress público. Ownership se comprueba en servidor incluso si el shell oculta la acción.

Los teléfonos Cliente/delivery de Guatemala se validan en los DTO de perfil, direcciones guardadas y solicitudes delivery: ocho dígitos agrupados como `0000 0000`, con prefijo `+502` opcional para compatibilidad. La app formatea antes de enviar y el servidor repite la validación; las constraints SQL históricas siguen permitiendo valores anteriores, así que no se debe tratar esa validación del API como limpieza automática de datos ya almacenados.

Los cierres de caja también requieren `Idempotency-Key`: si la respuesta se pierde después del commit, repetir el mismo payload devuelve el cierre existente; reutilizar la clave con otro monto o versión produce `409`. La clave y el cierre se confirman en la misma transacción para evitar arqueos finales o auditorías duplicadas. Los arqueos intermedios siguen la misma regla: `POST /api/v1/operational/cash-sessions/{sessionId}/reconciliations` exige clave, el fingerprint incluye sesión/monto/notas normalizados y el replay recupera el mismo arqueo aun después de cerrar la caja. La restricción evita duplicados también ante dos requests simultáneos con la misma clave.

Las claves compartidas de `IdempotencyStore` duran 24 horas. Dentro de esa ventana el mismo contenido reproduce el recurso ya confirmado y el contenido distinto responde `409`; después del vencimiento, la misma clave puede reclamar una nueva operación. Un lease `IN_PROGRESS` vencido se puede reclamar con el mismo fingerprint. `IdempotencyKeyCleanupWorker` borra hasta 500 filas vencidas por hora en transacción corta, omitiendo filas bloqueadas por operaciones activas.

La administración de catálogo usa `/api/v1/admin/catalog` bajo `catalog:manage` (ADMIN): categorías, áreas de preparación, alta/edición de productos, grupos, opciones, vínculos e impactos auditados con control optimista. Los nuevos productos se crean ocultos/inactivos, sin tracking de inventario, con receta `PENDING_DATA`; sólo personal autorizado los publica tras revisar su configuración. El menú público expone `/api/v1/public/menu` y lectura individual por UUID o slug (`/products/{idOrSlug}`), con precio `BigDecimal`/GTQ, grupos activos y `ageRestricted`. El seed repetible `database/seeds/menu_real_dev.sql` crea el menú vigente para desarrollo, sin ejecutar ingredientes, cantidades, existencias, conversiones ni consumos. La receta queda separada del catálogo. Un BOM guardado para producto de menú no reserva ni estima stock mientras `recipe_status` no sea `ACTIVE`; la API de inventario permite activar explícitamente una receta con componentes rastreados y audita el cambio. Evaluación pública y aceptación de pedidos leen el BOM activo bajo bloqueo compartido del producto, de modo que no compitan con una edición/activación concurrente. Los componentes de subproductos usados por producción mantienen su flujo independiente. Solicitudes pickup/delivery validan min/max, scope y estado de cada opción contra el catálogo; precio, fingerprint idempotente y snapshots quedan en la solicitud. Al aceptar, la API vuelve a validar precio/configuración, copia opciones al pedido y ajusta reservas sólo por impactos de receta explícitamente configurados. `POST /api/v1/public/menu/availability` calcula una estimación sin reservar existencias; los productos del menú real quedan `NOT_TRACKED` hasta activar recetas e inventario. Edad +18 se transmite como marca de dominio, pero el procedimiento legal de verificación de edad queda pendiente de definición y no se afirma implementado.

Las cancelaciones de solicitudes aún pendientes se separan por modalidad: `/api/v1/client/order-requests/{id}` sólo cancela PICKUP y `/api/v1/client/delivery-requests/{id}` sólo DELIVERY. Ambos validan propiedad, bloquean la solicitud mientras cambia de estado, son idempotentes tras la cancelación y no permiten cancelar una solicitud ya aceptada.

Para pedidos pickup/delivery ya aceptados, el Cliente puede enviar una solicitud de cancelación con motivo en `POST /api/v1/client/order-requests/{requestId}/change-requests`. La solicitud conserva la versión del pedido, emite eventos auditables, y no cambia el estado hasta una decisión Operativa con permiso `orders:manage`. Tanto el envío del Cliente como la decisión Operativa requieren `Idempotency-Key`; repetir la misma clave y payload recupera el recibo original, y usarla con contenido distinto responde conflicto. La aprobación revalida versión/estado, bloquea la cuenta y exige que el saldo capturado quede reembolsado manualmente antes de reutilizar la transición de `OrderService` que libera reservas y cancela comandas/despacho. No se aceptan solicitudes después de asignar o iniciar el reparto. No existe todavía edición de líneas ni reembolso automático.

El reporte agregado de ventas `GET /api/v1/admin/reports/sales/daily?from={date}&to={date}` es de solo lectura y exclusivo de ADMIN. Limita consultas a 31 días y no permite fechas futuras; agrupa por fecha de negocio `America/Guatemala` y moneda, y separa ventas capturadas, reembolsos, ventas netas, propinas y devoluciones de propina. No suma monedas distintas ni considera el fondo inicial de caja como venta. Los reembolsos se contabilizan el día en que se registran, no alteran retroactivamente el día de captura.

WOK es emisor de sesión: access JWT firmado de 10–15 min configurable; refresh opaco aleatorio y hash persistido por familia/sesión, rotado en cada uso con detección de reuse. `iss` debe ser una URI válida; `WOK_AUTH_ISSUER` configura el URL canónico por ambiente y el valor `.invalid` sólo permite desarrollo local. Registro público sólo CLIENT y `PENDING_VERIFICATION` hasta challenge de un uso. Google OIDC usa `sub`, requiere nonce server-issued de un solo uso y nunca asigna roles WOK; correos existentes no se vinculan automáticamente. Staff crítico puede acceder con método local durante corte WAN.

## Operación local y salud

Nginx recibe 80/443, Spring y PostgreSQL quedan privados. Un único hostname API se resuelve a IP privada en LAN y a ingreso público fuera. Sin WAN, core local sigue con mesas, pedidos, KDS, caja, inventario y administración. Solicitudes que no llegaron no se transforman en pedidos; al reconectar se revalidan. `CORE READY` y salud de Meta/FEL/pagos/email/IA se reportan por separado. Servidor, router, switch y AP principal necesitan UPS y backup probado.
