# Correo transaccional y dominio

Revisión de alternativas: 2026-09-25. El backend usa `EmailProvider`/outbox; no espera SMTP dentro de la transacción de registro, reset, reserva, pedido o FEL. El worker reintenta con backoff y marca entrega/fallo sin duplicar el caso de uso. Mailpit sirve sólo para desarrollo; no es entrega real.

| Opción                                                                                           | Ajuste al caso WOK                                                                                  | Costo operativo/TCO a medir                                                         |
| ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| [Stalwart](https://stalw.art/docs/install/get-started/)                                          | Servidor abierto con SMTP y buzones/protocolos; útil si WOK también administrará correo del dominio | Servidor, IP reputada, DNS, seguridad, backups, actualizaciones y monitoreo propios |
| [mailcow](https://docs.mailcow.email/)                                                           | Suite de correo/groupware en Docker; más completa que sólo notificaciones                           | Varios contenedores y operación de mail completa, reputación e incidentes           |
| [Postal](https://docs.postalserver.io/)                                                          | Plataforma abierta enfocada en entrega transaccional y webhooks                                     | Operar infraestructura de envío, DNS, IP/reputación y upgrades propios              |
| [Relay SMTP externo, por ejemplo SES](https://docs.aws.amazon.com/ses/latest/dg/send-email.html) | Entrega saliente sin operar MTA completo; puede combinarse con buzones propios                      | Pago por volumen/servicio, dependencia WAN y credenciales externas                  |
| Híbrido                                                                                          | Buzones autoalojados con relay externo para salida transaccional                                    | Dos componentes, pero reduce carga de reputación del envío directo                  |

Recomendación provisional: mantener el puerto `EmailProvider` intercambiable y usar relay saliente para correo transaccional productivo si las pruebas de entregabilidad/costo lo favorecen. La preferencia open source no justifica perder códigos de verificación en spam. No se elige proveedor ni precio sin dominio, volumen estimado, capacidad operativa y pruebas de inbox. Con WAN caída el outbox espera; el core LAN permanece operativo, pero un **nuevo** registro que necesita correo puede quedar pendiente de verificación.

DNS a preparar para el dominio elegido: `www`, `api`, `app`, `mail`, `go`, `status`; registros A/AAAA/CNAME según exposición, MX para recepción, SPF, DKIM y DMARC para autenticación. Verificar TLS, reverse DNS/reputación del IP de salida, límites de proveedor y política de rebote antes de uso productivo. No poner contraseñas SMTP ni API keys en repositorio, frontend o app.
